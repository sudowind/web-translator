# PDF 长文档按需翻译与性能优化设计

日期：2026-09-03  
状态：待评审

## 1. 背景

PDF 工作台当前采用“完整读取 PDF、MinerU 整篇解析、从第 1 页开始以并发 2 顺序翻译全文”的流程。PDF Canvas 已限制为活动页前后各 2 页，但译文页面、译文区块和 Markdown/KaTeX 内容仍按整篇文档挂载。

真实样本 `https://arxiv.org/pdf/2510.12403` 暴露了长文档退化：

- 76 页，文件大小 37,418,212 字节，约 35.7 MiB；
- 约 26.9 万文本字符；
- 43 张独立图片，压缩图片数据约 34.2 MiB，总像素约 1.86 亿；
- 当前 Base64 传输会把 37,418,212 字节扩张为 49,890,952 个字符；
- 当前同算法本机压力测量中，Base64 编码约 2.60 秒、解码约 0.19 秒；该测量不等同于 Chrome 实际进程数据，但证明整文件编解码属于一级成本；
- 现有 PDF 工作台 E2E 使用 2 页小型 PDF，没有覆盖长文档的调度、DOM 规模和内存退化。

用户阅读长论文时通常只访问部分页面。默认翻译全部 76 页会产生不必要的 LLM 请求、等待时间和界面更新，也会让后续每一页回填持续触发大范围 React 渲染。

## 2. 设计目标

本次设计包含以下不可分割的目标：

1. 长文档默认按需翻译，只翻译当前阅读位置及少量相邻页面；用户可以显式切换为全文翻译。
2. 未请求和离屏页面不得挂载完整译文区块，控制长文档 DOM、Markdown 和 KaTeX 工作量。
3. Agent 流式回答、页级翻译状态和区块高亮不能使整篇阅读流重新渲染。
4. 移除大 PDF 的后台到内容脚本 Base64 主传输路径，减少整文件复制、编码和跨上下文消息成本。
5. PDF.js 页面尺寸读取和页面资源按需处理，避免加载或缩放时一次操作全部页面。
6. 批量恢复已缓存译文，并在后台会话内复用文档模型，避免按页重复读取完整 `DocumentModel`。
7. 保留既有 PDF 接管、认证上传同意、MinerU URL 优先、逐页缓存、错误诊断和 Agent 能力。

## 3. 非目标

- 本次不处理跨页段落识别、合并或上下文补全。
- 不把多页内容合并为一个 LLM 请求，不改变当前“一页一个翻译请求”的 Provider 协议。
- 不实现逐块或逐字译文流式展示。
- 不要求 MinerU 在整篇解析完成前增量返回页面。
- 不改变表格和图片仅翻译标题、不渲染媒体正文的规则。
- 不新增 `file://` 支持，不扩大静态主机权限。
- 不新增全文导出、打印、搜索或缩略图侧栏。
- 不在本次设计中持久化用户的翻译模式偏好；重新打开文档时重新按文档规模选择默认模式，但继续复用已缓存页面。

## 4. 覆盖关系

本规格覆盖以下既有行为：

- 覆盖“PDF 逐页等高滚动与顺序翻译”中所有文档默认从第 1 页翻译到最后一页的调度规则；短文档和用户显式选择全文翻译时仍保留顺序派发。
- 覆盖“PDF 大文件源字节生命周期”中首次后台到内容脚本必须使用 Base64 传输的规则；描述信息、认证同意和 hash 复核规则继续有效。
- 扩展“PDF 翻译失败诊断与滚动渲染稳定性”中的 Canvas 窗口，只改变译文正文挂载、状态隔离和资源释放，不降低现有稳定性要求。

## 5. 长文档判定与翻译模式

### 5.1 判定规则

MinerU 返回 `DocumentModel` 后计算可翻译字符数。字符数只统计实际进入 `translationBlocksForPage` 的文本、列表、标题、脚注以及表格/图片标题，不统计公式、图片路径、表格 HTML 和被过滤的页眉页脚。

满足任一条件即视为长文档：

- `pageCount >= 30`；
- 可翻译字符数 `>= 100_000`。

阈值必须定义为有名称的纯逻辑常量并由单元测试覆盖，后续可根据基准调整，不能散落在组件中。

### 5.2 模式

工作台支持两种会话级模式：

- `on-demand`：按需翻译；长文档默认模式。
- `full-document`：全文翻译；短文档默认模式，或由用户显式启动。

模式切换只影响尚未派发的页面：

- 已完成、已缓存和失败页面状态保持不变；
- 已发出的请求不取消，避免浪费已经产生的请求和 token；
- 从全文切换为按需时，清除尚未派发的全文后台队列，再按当前阅读窗口重建按需队列；
- 从按需切换为全文时，把所有尚未完成的页面按页码递增加入全文队列。

## 6. 按需翻译调度

### 6.1 请求窗口

按需模式以已确认的活动页和阅读方向建立请求窗口：

1. 当前页；
2. 阅读方向上的下一页；
3. 阅读方向上的第二页；
4. 反方向上的相邻一页。

初次进入文档、尚无方向时，按“当前页、后 1 页、后 2 页、前 1 页”排序并裁剪到合法页码。

显式页码跳转、Agent 页码引用和上一页/下一页按钮立即更新请求窗口。连续滚动产生的活动页变化经过 350 毫秒稳定期后再加入新页面，避免快速掠过几十页时发送无意义请求；已经缓存的页面可以立即显示，不受稳定期限制。

Canvas 和译文正文的渲染窗口仍立即跟随浏览器观察到的主可见页，350 毫秒稳定期只约束新的 Provider 请求，不得用防抖延迟可见页面渲染或工具栏页码反馈。

### 6.2 优先级

调度优先级从高到低为：

1. 用户手动重试的当前页；
2. 显式导航到达的当前页；
3. 稳定可见的当前页；
4. 阅读方向预取页；
5. 反方向相邻页；
6. `full-document` 模式中的顺序后台页。

并发数默认保持为 2。本次不根据 Provider 自动提高并发数。

### 6.3 调度器状态

新的调度器至少维护：

- `mode`；
- `queued`，包含页码和优先级；
- `inFlight`；
- `done`；
- `failed`；
- `cached`；
- 最近一次稳定活动页和阅读方向。

同一页在任一时刻只能存在于一个有效状态。队列重排不得重复派发正在执行、已完成或已缓存的页面。单页失败不阻塞其他按需页面；内部 3 次自动尝试和手动重试规则保持不变。

### 6.4 全文模式

短文档默认全文翻译。长文档由用户选择“翻译全文”后进入全文模式。

全文模式保持页码递增派发，但当前页尚未翻译时允许提升当前页优先级。已经在执行的页面不取消，提升当前页不能永久饿死顺序队列。

## 7. 界面与交互

### 7.1 工具栏

工具栏或“更多”菜单显示当前翻译模式：

- 长文档初始显示“按需翻译”；
- 短文档初始显示“全文翻译”；
- 按需模式提供“翻译全文”；
- 全文模式提供“改为按需”，只停止尚未派发的后台页面。

不新增永久占位的复杂模式选择器；优先复用现有“更多”菜单，避免压缩窄屏工具栏。

### 7.2 状态文案

按需模式不再使用会暗示全文任务正在运行的单一进度文案。推荐格式：

`当前页已完成 · 已缓存 8/76 页 · 正在预取 2 页`

可能状态包括：

- 当前页等待翻译；
- 当前页翻译中；
- 当前页已完成；
- 当前页失败；
- 相邻页预取中；
- 已缓存页数；
- 全文模式下的完成、执行中和失败页数。

状态更新必须继续使用 `aria-live="polite"`，但不得为每个快速滚动经过的页面播报队列变化。

### 7.3 未请求页面

未进入请求窗口且没有缓存结果的页面显示轻量状态：

`滚动到本页后自动翻译`

该状态可以提供“翻译本页”按钮。按钮必须达到 44×44px 热区并具有明确可访问名称。未请求页面不能显示“翻译中…”。

### 7.4 已缓存页面

已缓存页面在进入渲染窗口时直接显示译文，不重新请求 Provider。离屏卸载译文正文不影响缓存状态或完成计数。

## 8. 译文渲染架构

### 8.1 页面壳与正文分离

所有页面继续保留固定高度的轻量 `PagePair` 页面壳，用于：

- 保持逐页等高；
- 保持文档总高度和滚动位置；
- 支持 `IntersectionObserver`；
- 支持页码跳转。

只有活动页前后各 2 页组成的译文渲染窗口挂载完整 `TranslationPage` 正文。窗口外页面只保留页头和轻量占位，不遍历 `page.blocks`，不创建 `ReactMarkdown`、KaTeX 或交互区块。

Canvas 窗口和译文窗口初始均使用活动页前后各 2 页，但二者使用独立命名的窗口函数，避免未来调整一个窗口时意外改变另一个窗口。

### 8.2 页内滚动恢复

译文正文卸载前把该页 `scrollTop` 保存到内存中的页码映射；重新进入渲染窗口时恢复。该映射不写入 IndexedDB，关闭或刷新工作台后可以丢失。

译文回填、正文卸载和重新挂载不得改变外层页面高度或主滚动位置。

### 8.3 React 状态隔离

`PdfWorkspace` 不再把所有高频状态集中到一个会驱动整棵页面树的渲染边界。

至少拆分为：

- 阅读流容器：PDF 文档、页高、活动页、页级翻译快照；
- Agent 容器：Agent 消息、50 毫秒增量刷新、忙碌和错误状态；
- 工具栏状态：模式、摘要进度和导航操作。

要求：

- Agent 流式增量不能重新渲染阅读流；
- 某一页翻译完成不能重新渲染其他页的完整译文正文；
- 区块 hover 预览只更新关联页面的 PDF 高亮层；
- `TranslationPage` 使用页级稳定 props 和 `React.memo`，不能把每次都变化的全局 `translations` Map 直接传给所有页面；
- 回调必须稳定，不能因内联函数使页面级 memo 失效；
- 每页译文结果以页码为边界保存，更新一页时保持其他页对象引用不变。

### 8.4 浏览器布局兜底

页面壳使用 `content-visibility: auto` 与合理的 `contain-intrinsic-size` 作为离屏布局和绘制兜底。固定页高仍由现有页高映射控制，CSS 优化不得导致页码跳转、IntersectionObserver 或截图验收失真。

## 9. PDF.js 加载与资源生命周期

### 9.1 页面尺寸

页面尺寸使用 scale=1 的基础尺寸缓存：

- 首次只读取活动页前后各 2 页；
- 其余页面在浏览器空闲时间分批读取，每批最多 4 页；
- 未读取页面使用已知最近页面或第一页宽高比作为占位估算；
- 实际尺寸到达后只更新高度确有变化的页面；
- 缩放只根据基础尺寸重新计算，不重新对全部页面调用 `getPage()`。

空闲批处理不是页面渲染，不得创建 Canvas 或文本层。

### 9.2 Canvas 与文本层

活动页前后各 2 页的稳定 Canvas 窗口保持不变。页面离开窗口时：

- 取消尚未完成的 render task 和文本层；
- 清空 Canvas 和文本层 DOM；
- 在确认没有进行中的渲染后调用页面级 `cleanup()`；
- 再次进入窗口时允许 PDF.js 重新加载该页资源。

超大图片页面不能因为离开窗口后仍保留 Canvas、文本层或页面渲染资源而持续抬高内存。

## 10. PDF 源字节路径

### 10.1 目标路径

首次读取改为内容脚本对当前标签页 URL 进行同源读取：

1. 内容脚本先以 `credentials: 'omit'` 读取当前 URL；响应失败或不是 PDF 时，再以 `credentials: 'include'` 读取一次并把来源标记为认证 PDF；
2. 验证 `%PDF-` 签名，并继续从最终响应头和 URL 解析安全标题；
3. 直接对原始 `ArrayBuffer` 计算 SHA-256，不创建 `Uint8Array.from()` 副本；
4. 生成不含字节的 `PdfSourceDescriptor`；
5. 把字节所有权交给 PDF.js，不在 React 状态中长期保留第二份 `Uint8Array`；
6. `pdf:parse-start` 继续只向后台发送描述信息。

生产消息中不再存在 `PdfSourceTransfer.bytesBase64`，大 PDF 不通过 `browser.runtime.sendMessage` 传输整文件字符串。

### 10.2 后台上传回退

后台仅在以下情况重新读取 URL：

- 认证 PDF 已获得明确上传同意；
- 公共 URL 的 MinerU 任务失败，需要执行既有的单次上传回退。

重取后必须重新计算 SHA-256，并与内容脚本提供的 `PdfSourceDescriptor.hash` 比较；不一致时返回 `PDF_SOURCE_CHANGED`，不得上传新内容。

公共 URL 仍优先创建 MinerU URL 任务。认证 PDF 在用户同意前，后台不得为了上传而读取或缓存文件字节。

### 10.3 浏览器可行性门禁

源字节路径属于 PDF 接管和权限高风险范围。实现前只允许一次有证据的真实浏览器可行性验证，覆盖：

- 当前 arXiv 公共 PDF；
- 已授权 HTTP(S) 测试源；
- 带 Cookie 的认证 PDF 测试源；
- URL、hash、标题、页数和原始页面恢复。

如果内容脚本同源读取被浏览器边界阻止，不反复探索规避方式；暂停本小节实现，记录证据并修订为分块 Port 或独立扩展页面方案。其他渲染和调度里程碑不因此阻塞。

## 11. 缓存恢复与后台模型复用

### 11.1 批量译文快照

新增批量读取能力，根据以下完整键空间读取当前文档的有效译文：

- hash；
- source language；
- target language；
- provider；
- model；
- 每页 schema。

工作台获得 `DocumentModel` 后只发送一次批量快照请求。响应按页返回合法且 block ID 完整匹配的译文；损坏或 schema 不匹配的单页作为未缓存处理，不能使整个快照失败。

调度器在首次派发前用快照初始化 `cached` 和 `done`，避免重新打开文档时通过 76 次 `pdf:translate-page` 消息逐页探测缓存。

### 11.2 后台文档模型

`PdfWorkspaceService` 在 Service Worker 当前生命周期内维护一个最多 3 份文档的 LRU 模型缓存：

- 解析完成或从 IndexedDB 读取后写入；
- `pdf:translate-page` 和 Agent 请求优先读取内存模型；
- 未命中时回退 IndexedDB；
- 清除文档缓存时同步移除内存项；
- Service Worker 重启后允许自然丢失，不改变持久化语义。

这样可避免每页翻译都从 IndexedDB 结构化克隆完整长文档。

## 12. MinerU 结果处理

MinerU ZIP 只需要 `_content_list.json`。解压时必须使用 `fflate` 的 `filter` 跳过图片和其他未使用文件，不能先同步展开整个 ZIP 再筛选。

内容列表仍按当前规则完成 JSON 校验和规范化。过滤优化不得改变表格、图片标题、标题层级、公式和页眉页脚过滤结果。

## 13. 数据与消息模型

建议新增或调整以下类型：

- `TranslationMode = 'on-demand' | 'full-document'`；
- `PageTranslationState`：页码、状态、结果、失败、尝试次数和来源 `cache | provider`；
- `TranslationSnapshotPage`：页码及该页译文数组；
- `pdf:translation-snapshot`：只携带 hash，由后台使用当前设置解析完整缓存键；
- 移除生产消息中的 `PdfSourceTransfer` 和 `pdf:source` 整文件响应。

所有新增消息继续使用精确键验证，拒绝未知字段、越界页码、字节载荷和凭据。快照响应不得包含原文、Prompt、API Key 或 Provider 原始响应。

## 14. 异常与边界行为

- MinerU 尚未完成时记录最新活动页；模型到达后优先调度该页，而不是固定第 1 页。
- 快速滚动跨越多页时，只对稳定停留后的窗口排队。
- 当前页没有可翻译区块时立即标记完成，不调用 LLM。
- 当前页失败后继续预取其他页面；失败页仅通过既有自动尝试或用户手动重试重新入队。
- 模式切换、清缓存、关闭工作台和标签页导航必须清除尚未派发队列并取消当前会话。
- 页面数不一致时，以 PDF.js 验证后的页数作为导航边界；MinerU block 越界继续按现有规则拒绝。
- 离屏译文正文卸载不能丢失已完成译文、失败诊断和页内滚动记录。
- Agent 继续基于原始 `DocumentModel` 构建上下文，不依赖全文译文是否完成。

## 15. 性能基准与测试策略

### 15.1 确定性长文档基准

新增运行时生成的长文档测试夹具，不把 37 MiB PDF 提交进仓库：

- 76 页 PDF；
- 76 页 `DocumentModel`；
- 每页包含标题、正文、列表、公式和媒体标题的代表性区块；
- 单独生成约 36 MiB 的字节输入验证源路径，不依赖外网；
- 可选的真实 arXiv 验收不作为日常发布门禁。

### 15.2 单元测试

- 长文档阈值和可翻译字符统计。
- 按需窗口、阅读方向、350 毫秒稳定期和边界裁剪。
- 优先级、并发 2、去重、失败和模式切换。
- 缓存快照初始化后不重复派发已缓存页面。
- LRU 模型缓存命中、淘汰和清缓存失效。
- 源描述信息不包含 Base64、ArrayBuffer 或 `number[]`。

## 16. 验收标准

- 76 页或 10 万可翻译字符以上的文档默认进入按需模式。
- 初次停留只翻译当前页及最多 3 个相邻页面，不自动消耗全文请求。
- 用户可以显式翻译全文，也可以返回按需模式而不取消已发出的请求。
- 未请求或离屏页面不挂载完整 Markdown/KaTeX 译文区块，逐页等高和主滚动位置保持稳定。
- Agent 流式回答、页级状态和 hover 高亮不再使整篇阅读流重渲染。
- PDF.js 初始加载和缩放不再同步读取全部页面尺寸；离开窗口的重型页面资源可以释放。
- 大 PDF 首次读取不再通过扩展消息传输 Base64 整文件；认证同意、公共 URL 优先和 hash 变化保护保持有效。
- 已缓存译文通过一次快照恢复，已缓存页不调用 Provider。
- 每页翻译和 Agent 请求优先复用后台内存模型，不重复读取完整 `DocumentModel`。
- MinerU ZIP 不解压未使用的图片和其他文件。
- 跨页段落行为保持现状，没有被本轮隐式修改。
- 相关定向测试、类型检查、生产构建、完整 `npm run check` 和 PDF 工作台 E2E 在当前提交上通过。
