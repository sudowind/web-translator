# PDF 紧凑对译布局与缩放清晰度设计

日期：2026-09-03  
状态：已实现

后续补全：本规格的原始 2 倍上限、仅主导页最终质量与预览 CSS 行为已由 `docs/superpowers/specs/2026-09-04-pdf-visible-page-sharpness-design.md` 修正。以下保留历史设计背景，当前清晰度规则以后续规格为准。

## 1. 背景

当前 PDF 工作台使用全宽页对网格：

- 页对第一列为 `minmax(0, 1fr)`，PDF Canvas 在第一列内居中；
- 第二列为 `minmax(320px, .72fr)`，译文会跟随超宽视口持续变宽；
- 智能体侧栏展开后，仍主要依赖浏览器视口断点决定页对是否改为上下布局；
- PDF Canvas 先按工具栏缩放比例生成，再由 `max-width: 100%` 在 CSS 中二次压缩。

这组规则在常见笔记本宽度下基本可用，但在 2560px 等宽屏、180% 等较高缩放比例下会暴露两个明显问题：

1. PDF 右边缘与译文左边缘之间出现远大于设计间距的空白。空白来自 PDF 列的剩余轨道，不是显式 `gap`，因此单纯修改 `gap` 无法解决。
2. 译文列一直延伸到右侧，中文行长过长，眼睛回行距离大；智能体展开时两列又可能被压得过窄。
3. Canvas 的渲染尺寸、CSS 显示尺寸和设备像素比没有统一的最终度量。缩放时旧画布会被拉伸或可见画布被直接清空重绘，容易出现短暂模糊、局部绘制和文字层错位。
4. 直接为所有活动窗口页面提高像素密度会显著增加 Canvas 内存、PDF.js 渲染任务和主线程负担，不符合长文档按需渲染的既有性能目标。

本设计把布局与清晰度视为同一个问题：先算出页面真实显示尺寸，再按该尺寸生成有像素预算的 Canvas，不允许 CSS 在事后偷偷改变画布比例。

## 2. 产品定位与单一任务

- 具体产品：面向论文和技术 PDF 的逐页原文/译文阅读工作台。
- 主要用户：需要长时间对照阅读、引用原文并随时向论文智能体提问的研究者和工程师。
- 页面单一任务：让用户以最低的横向视线移动成本，持续核对同一页原文与译文。

设计重点不是“把屏幕填满”，而是让原文、译文和可选智能体形成有明确阅读优先级的工作台。

## 3. 目标

- PDF 的可见右边缘与译文的可见左边缘之间只保留一个明确、稳定的对译沟槽。
- 宽屏剩余空间平均回到整组内容两侧，不聚集在两列正中间。
- 译文保持适合中文连续阅读的行长，不因超宽屏无限扩张。
- 缩放、窗口变化和智能体开关均使用阅读区真实宽度计算布局。
- 用户快速连续缩放时，不展示被放大的低分辨率 Canvas，也不展示 PDF.js 的半成品帧。
- 清晰度提升受像素、并发和页面窗口预算约束，不回退长文档性能优化。
- 保持逐页等高、单主滚动、区块联动、文本选择和智能体 sticky 行为。

## 4. 非目标

- 不改变 PDF/译文的内容结构、翻译顺序、缓存协议或 Provider 行为。
- 不增加可拖拽分栏；本轮先用确定性规则建立稳定基线。
- 不把主阅读区改成自由横向滚动的无限画布。
- 不重新设计工具栏、智能体内容或全局色彩品牌。
- 不承诺所有 PDF 页面在 300% 下仍与译文并排；当真实空间不足时，应稳定切换为上下布局。

## 5. 视觉方向

### 5.1 核心概念：对译书脊

原文与译文被视为一张摊开的双语书页，而不是两个互不相关的全宽面板。两者之间的窄沟槽是唯一的视觉签名，称为“对译书脊”。

这项选择的风险是放弃传统仪表盘式的等比例铺满，改用明显不对称的内容宽度；理由是 PDF 的宽度由纸张决定，译文的宽度由可读行长决定，两者本来就不应使用同一种 `fr` 逻辑。

### 5.2 紧凑视觉令牌

沿用现有克制的编辑型界面，不引入新的装饰体系：

- 纸张白：`#FFFFFF`，PDF 和译文承载面；
- 工作台灰：`#F3F4F6`，两侧呼吸空间；
- 正文墨色：`#111827`；
- 次级石墨：`#667085`；
- 交互靛蓝：`#4F46E5`；
- 分隔线：`#E5E7EB`。

字体角色保持系统原生以保证扩展加载稳定：

- PDF 原文：由 PDF 自身字形决定；
- 译文正文：系统中文无衬线，15px，行高 1.62；
- 页码、状态和缩放值：系统 UI 字体，13px，使用 tabular nums。

本轮的视觉辨识度来自精确的内容宽度与书脊间距，不来自新增颜色、圆角或阴影。

## 6. 布局模型

### 6.1 术语

- `C`：`.reading-stream` 的实际可用内联宽度，已经扣除工作台 padding 和智能体侧栏。
- `P0`：PDF 页面在 100% 下的基础宽度。
- `Z`：用户请求的缩放比例。
- `P = P0 × Z`：本次缩放请求的目标 PDF 宽度。
- `G`：对译书脊宽度。
- `Tideal`：译文理想宽度。
- `Tmin`：译文双列模式下的最小宽度。
- `W`：原文与译文组合后的页对宽度。

### 6.2 固定约束

- `G = clamp(12px, 0.8vw, 20px)`；
- `Tideal = clamp(520px, C × 34%, 720px)`，比例基于阅读区容器而不是浏览器视口；
- `Tmin = 480px`；
- 工作台外层 padding 沿用现有值，宽屏可收敛到 16–24px；
- 译文正文继续使用自身 16–18px 内边距；
- 双列模式下 PDF 页面与译文顶部对齐、外层等高。

`720px` 是译文承载面的上限，不是正文行盒宽度；扣除内边距后，常规 15px 中文正文约为 42–46 个全角字符，避免截图中超过舒适回行距离的长行。

### 6.3 双列分配算法

先以阅读区容器而不是浏览器视口做判断：

1. 若 `P + G + Tmin <= C`，使用双列模式。
2. 译文宽度取 `T = min(Tideal, C - P - G)`。
3. 页对宽度取 `W = P + G + T`。
4. 页对以 `margin-inline: auto` 居中；PDF 列宽严格为 `P`，译文列宽严格为 `T`。
5. PDF 在自己的列内不再居中留空，译文也不再吞掉全部剩余宽度。

这样，PDF 可见右边缘到译文可见左边缘的距离恒等于 `G`，而不是 `G + PDF 轨道剩余空间`。

### 6.4 上下模式

以下任一条件成立时改为上下模式：

- `P + G + Tmin > C`；
- 阅读区宽度小于 900px；
- 浏览器处于现有移动布局范围。

上下模式中：

- PDF 在上，译文在下，保持 DOM 阅读顺序；
- PDF 显示宽度为 `min(P, C)`；
- 译文宽度为 `min(720px, C)` 并居中；
- 两者之间使用 12–16px 垂直间距；
- 页面高度为 PDF 高度、垂直间距和译文外层高度之和，不再强行使用双列页对高度。

为防止智能体开关、滚动条出现或窗口轻微变化导致布局来回抖动，模式切换使用 48px 滞回区：进入上下模式后，只有可用宽度重新多出至少 48px 才恢复双列。

### 6.5 布局示意

宽屏、智能体收起：

```text
|       外侧留白       | PDF 原页 | 12–20 | 译文 ≤ 720 |       外侧留白       |
|                      |          对译书脊           |                      |
```

宽屏、智能体展开且空间仍充足：

```text
|   外侧留白   | PDF 原页 | 12–20 | 译文 ≤ 720 | 16 | 智能体 340–360 |
```

智能体展开或高倍缩放后空间不足：

```text
|          PDF 原页，按请求宽度居中          | | 智能体 |
|             译文 ≤ 720，居中               | | 侧栏   |
```

移动端智能体继续使用现有覆盖式面板，不参与页对列宽。

## 7. 缩放语义与滚动稳定性

### 7.1 请求缩放与显示缩放

工具栏缩放值表示用户请求的 PDF 页面比例。双列模式只有在该请求可以同时保住 `Tmin` 时存在；不再通过 CSS 静默压缩 PDF 来伪装成该缩放比例。

当请求比例无法放入双列时，布局改为上下模式，让 PDF 尽可能按请求比例显示。若 `P > C`，本轮仍以 `C` 为上限，不引入主页面横向滚动；工具栏应通过可访问状态文本提示“已适配阅读区宽度”。

### 7.2 当前页锚点

缩放或布局模式变化前记录：

- 当前主导页页码；
- 当前页相对视口顶部的进度；
- 当前页译文内部 `scrollTop`。

新页高提交后恢复到同一页的近似进度，允许误差不超过 8px。不得因为前面几十页的高度重算把当前页推离视口。

### 7.3 交互提交

- 工具栏数值立即响应点击。
- 连续缩放使用 100–140ms 空闲防抖，避免每次 10% 点击都启动五页完整重绘。
- 防抖最多延迟 220ms；达到上限时必须提交最新缩放，避免持续按键时长期不更新。
- 仅最新缩放 generation 可以成为可见帧，过期任务必须取消或丢弃。
- `prefers-reduced-motion` 下不使用平滑滚动或尺寸过渡。

## 8. Canvas 清晰度模型

### 8.1 单一显示度量

新增纯逻辑度量函数，建议接口：

```ts
interface PageDisplayMetrics {
  cssWidth: number;
  cssHeight: number;
  displayScale: number;
  outputScale: number;
  bitmapWidth: number;
  bitmapHeight: number;
}

computePageDisplayMetrics(baseSize, requestedScale, allocatedWidth, devicePixelRatio, pixelBudget)
```

布局先确定 `cssWidth` 和 `cssHeight`。Canvas、文本层、高亮层和页对高度都消费同一份度量：

- Canvas CSS 尺寸严格等于 `cssWidth × cssHeight`；
- PDF.js viewport 使用 `displayScale = cssWidth / P0`；
- Canvas 位图尺寸为 CSS 尺寸乘 `outputScale`；
- 文本层与高亮层使用显示 viewport，不使用位图 viewport；
- 删除依赖 `max-width: 100%` 的画布二次缩放路径。

### 8.2 设备像素比与像素预算

最终输出倍率：

```text
budgetScale = sqrt(MAX_CANVAS_PIXELS / (cssWidth × cssHeight))
outputScale = clamp(min(devicePixelRatio, budgetScale), 1, 2)
```

初始预算：

- 最终质量单页 `MAX_CANVAS_PIXELS = 8,388,608`（约 8 Mi 像素）；
- `outputScale` 最大为 2；
- 单个 RGBA Canvas 理论上限约 32 MiB，不包含 PDF.js 临时资源；
- 若 CSS 页面本身已经超过预算，仍保证 1x，不用小于 1 的倍率制造确定性模糊，同时由布局最大宽度限制极端页面。

浏览器缩放、窗口跨显示器或 `devicePixelRatio` 变化时，只让当前页和即将进入视口的页面失效重绘，不扫描全部文档。

### 8.3 双缓冲与原子换帧

当前实现会修改可见 Canvas 的 `width/height` 后直接让 PDF.js 绘制。修改位图尺寸会立刻清空画布，而 PDF.js 绘制过程可能被用户看见。

新流程：

1. 保留上一张已完成的前台 Canvas。
2. 在未展示的后台 Canvas 上执行最新 generation 的 PDF.js render task。
3. 渲染成功后，一次性提交 Canvas、显示 viewport、文本层 render id 和高亮几何。
4. 新帧提交后再释放旧 Canvas；失败或取消时继续显示旧帧并呈现错误状态。
5. 不允许新 Canvas 与旧文本层、旧 Canvas 与新文本层混搭。

这既消除半成品帧，也避免缩放过程中出现短暂空白。

### 8.4 缩放预览规则

- 缩小时，可以把旧的高分辨率前台帧向下缩放作为短暂预览，因为它不会损失有效像素密度。
- 放大时，不允许把旧帧放大到超过其有效 1 CSS 像素对应 1 位图像素的尺寸；在新帧完成前保持旧帧原尺寸并居中于目标页面槽位。
- 新帧完成后直接换到目标尺寸，不使用模糊的 transform 动画。
- 正在更新时可在页角显示不改变布局的轻量进度状态，但不得遮挡正文或夺取焦点。

## 9. 渲染性能策略

### 9.1 质量分层

保留现有活动页前后各 2 页的 Canvas 窗口，但不让五页同时以最高质量抢占资源：

- 当前可见主导页：最终质量，按设备像素比和 8 Mi 像素预算渲染；
- 即将进入视口的相邻页：预览质量，`outputScale` 上限 1.25；
- 窗口边缘页：只保留稳定占位，空闲时才生成 1x 预览；
- 页面成为主导页后升级到最终质量；离开窗口后沿用现有安全 cleanup。

最终质量 PDF.js render task 全局最多并发 2 个；预览任务不得抢占当前页最终任务。快速缩放或快速滚动时，取消尚未开始的过期任务。

### 9.2 内存与缓存

- 不建立跨整篇文档的高分辨率 Canvas 缓存。
- 每页最多保留一张前台帧和一张正在生成的后台帧。
- 换帧后立即把旧 Canvas 的 `width` 和 `height` 设为 0，再释放引用。
- 页面离开渲染窗口后释放前后台 Canvas、文本层和可释放的页面资源。
- 可以复用页面代理和 scale=1 基础尺寸缓存，不重新为缩放调用全部页面的 `getPage()`。

### 9.3 布局与渲染解耦

- `ResizeObserver` 只更新阅读区容器宽度和布局度量。
- 只有 `cssWidth`、`cssHeight` 或有效 `outputScale` 发生超过 0.5px/0.05 的变化时才触发重绘。
- 仅外侧留白变化而页面显示尺寸不变时，不重绘 Canvas。
- 智能体流式增量不得触发布局度量或 PDF 重绘。

## 10. 智能体侧栏协同

- 桌面侧栏继续为 340–360px sticky 区域，工作台与侧栏间距为 16px。
- 页对布局观察 `.reading-stream`，因此侧栏展开产生的真实宽度变化会自动进入同一算法。
- 侧栏展开后如果仍满足 `P + G + Tmin <= C`，继续紧凑双列；否则页对改为上下模式。
- 侧栏收起后使用滞回规则恢复双列，并恢复当前页锚点。
- 不为了强保三列而把译文压到 480px 以下，也不把 PDF 画布低分辨率拉伸。
- 侧栏自身滚动、输入框高度和流式消息继续与主阅读滚动隔离。

## 11. 响应式行为矩阵

| 阅读区条件 | 智能体 | 页对模式 | 译文宽度 | PDF 行为 |
| --- | --- | --- | --- | --- |
| `P + G + Tmin <= C` | 收起或展开 | 紧凑双列 | 480–720px | 按请求比例 |
| 空间不足但 `C >= 900px` | 常见于高倍缩放或展开侧栏 | 上下 | 最大 720px | 最大为阅读区宽度 |
| `C < 900px` | 桌面窄窗 | 上下 | 最大为阅读区宽度 | 最大为阅读区宽度 |
| 移动端 | 覆盖式面板 | 上下 | 全宽减 padding | 全宽减 padding |

布局规则必须覆盖 50%–300% 的全部工具栏缩放范围，不为 180% 添加特例。

## 12. 无障碍与状态

- DOM 顺序始终为第 N 页 PDF、第 N 页译文、下一页。
- 布局从双列切为上下不复制节点，不改变屏幕阅读器顺序。
- “已适配阅读区宽度”和“正在提高清晰度”使用 `aria-live="polite"` 的短状态，不在每次内部预览任务时重复播报。
- Canvas 换帧不抢焦点；文本选择在最新文本层提交后保持可用。
- 缩放按钮继续保持 44×44px 热区和可见焦点。
- 高对比度与强制颜色模式下，布局不能依赖阴影表达页面边界。

## 14. 测试策略

### 14.1 纯逻辑测试

- 50%、110%、180%、300% 下计算 `P/T/G/W`，可见中缝始终等于 `G`。
- 2560px 宽屏收起/展开智能体时，译文不超过 720px，页对整体居中。
- 1440px、1280px 和 900px 阅读区在空间不足时稳定进入上下模式。
- 48px 滞回区内不反复切换布局。
- 页尺寸、DPR 和 8 Mi 像素预算生成正确 bitmap 尺寸；`outputScale` 在 1–2 之间。
- 仅外侧留白变化、CSS 页面尺寸未变时不触发重绘判定。

### 14.2 组件测试

- 页对列宽来自统一布局度量，不再依赖 `1fr/.72fr`。
- Canvas 位图尺寸不小于 CSS 显示尺寸，且不超过单页像素预算允许值。
- 快速连续缩放只有最新 generation 原子提交。
- 放大等待期间旧 Canvas 不被 CSS 上采样；取消或失败保留旧帧。
- Canvas、文本层和高亮层总是使用同一个已提交 render id。
- 智能体流式消息不会创建新的 PDF render task。

### 14.3 Playwright 与视觉验收

至少覆盖：

- 2560×1271、180%、智能体收起，复现用户截图场景；
- 2560×1271、180%、智能体展开；
