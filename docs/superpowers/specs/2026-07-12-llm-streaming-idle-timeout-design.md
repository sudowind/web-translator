# LLM 流式翻译与空闲超时设计

## 背景与实验结论

PDF 页面翻译当前使用非流式 Chat Completions 请求，并要求 `response_format: { "type": "json_object" }`。客户端从请求开始设置固定总超时，模型即使仍在持续生成内容，也会在达到总时限后被中止。

2026 年 7 月 12 日使用同一百炼兼容接口、同一模型和同一合成论文页输入进行了对照实验：

- 12 个文本块、约 10059 个输入字符时，非流式 JSON Object 完成耗时 31402 毫秒；移除 `response_format` 后耗时 31876 毫秒。两者差异不足以说明 JSON Object 是主要耗时来源。
- 同一输入使用流式 JSON Object 时，717 毫秒收到首个文本片段，完整结束耗时 31688 毫秒，最终 JSON 与翻译结构均有效。
- 40 个文本块、约 33523 个输入字符时，流式 JSON Object 在 1187 毫秒收到首个文本片段，完整结束耗时 105672 毫秒；相邻文本片段最大停顿为 257 毫秒，最终 JSON 与翻译结构均有效。

因此，主要问题是长输出与固定总超时冲突，而不是 JSON Object 格式本身。流式传输不会缩短模型完整生成时间，但可以区分“连接持续健康”和“请求真正停滞”。

## 目标

- 翻译请求继续要求 JSON Object，保持现有结构化翻译协议和结果校验。
- 翻译请求使用 SSE 流式响应。
- 翻译配置中的超时时间改为“响应空闲超时”：只有连续达到该时长没有收到有效响应数据才中止请求。
- 收齐完整流式内容并通过现有 JSON 与块 ID 校验后，才把结果提交到页面状态与缓存。
- 保持连接测试和智能体请求的现有行为，不在本次改动中扩大范围。

## 非目标

- 本次不把单页翻译拆分为多个 LLM 请求。
- 本次不在翻译区域逐字展示尚未闭合的 JSON 内容。
- 本次不改变重试次数、页面翻译顺序或并发数。
- 本次不取消 `response_format`，也不降低翻译结果结构校验要求。

## 架构与组件

### 请求构建器

`buildChatRequest` 在翻译用途下同时设置：

- `response_format: { type: "json_object" }`
- `stream: true`

连接测试和智能体用途不自动启用流式响应，避免改变已有调用契约。

### Chat 客户端

`OpenAiChatClient.complete` 根据请求体中的 `stream` 选择响应读取方式：

- 非流式响应继续读取普通 JSON，并从 `choices[0].message.content` 取得文本。
- 流式响应按 SSE 行解析 `data:` 事件，忽略空行、注释和 `[DONE]`，累积 `choices[0].delta.content`。
- 流结束后返回完整文本，继续交给现有翻译响应解析器校验 JSON、数组结构和块 ID。

SSE 解析应作为独立的小型模块或纯函数实现，避免让 HTTP、计时器和协议解析全部耦合在一个方法中。

## 超时语义

翻译请求的 `timeoutMs` 改为空闲超时：

1. 发出请求时启动计时器。
2. 收到响应头后重置计时器。
3. 每收到一个有效 SSE 数据事件后重置计时器；事件不要求一定包含文本，以兼容 Provider 的角色、用量等事件。
4. 正常读完流、调用方取消或请求失败时清理计时器。
5. 连续空闲达到配置时长时中止请求，并沿用 `LLM_TIMEOUT` 到 `TRANSLATION_TIMEOUT` 的错误映射。

非流式连接测试和智能体请求仍使用当前固定总超时，避免本次改动改变其他功能。

## 数据流

1. 页面翻译服务生成整页 blocks。
2. 请求构建器生成流式、JSON Object 格式的翻译请求。
3. Chat 客户端建立请求并开始空闲计时。
4. SSE 解析器持续接收事件、刷新空闲计时器并累积文本。
5. 收到 `[DONE]` 或响应体正常结束后，将完整文本交给现有 `parseTranslationResponse`。
6. 只有完整校验通过后，页面状态才从“翻译中”变为“完成”并写入缓存。
7. 超时、网络中断、流格式错误或最终 JSON 无效时，继续进入现有失败诊断和重试流程。

## 错误处理与兼容性

- HTTP 非成功状态仍优先映射为具体 HTTP 错误，不尝试读取为成功 SSE。
- 响应声明为流式但缺少可读取响应体时，映射为响应无效。
- 单个非 JSON SSE 数据事件不能静默吞掉；除 `[DONE]` 外的无效数据应使请求以响应无效失败，便于诊断 Provider 不兼容。
- 流正常结束但没有任何文本，或累积内容无法通过现有翻译结构校验时，沿用现有响应无效或 Schema 错误。
- 调用方主动取消必须保持 `AbortError`，不能误报为超时。
- API Key 仅作为请求头使用，不进入日志、诊断详情、实验结果或测试快照。

## 测试策略

采用测试驱动开发，先验证失败再实现：

- 请求构建测试：只有翻译用途启用 `stream: true`，且仍保留 JSON Object。
- SSE 解析测试：跨 chunk 行、多个 `data:` 事件、`[DONE]`、无效事件和空内容。
- 空闲超时测试：持续收到事件时即使总耗时超过 `timeoutMs` 也不超时；连续无事件达到阈值时返回 `LLM_TIMEOUT`。
- 取消测试：调用方取消仍返回 `AbortError`。
- 非流式回归测试：连接测试和智能体普通 JSON 响应保持原行为。
- 翻译客户端回归测试：流式累积后的完整 JSON 继续通过现有 Schema 与 ID 校验。
- 最终运行类型检查、完整单元测试和构建；本次没有 UI 交互变化，不新增浏览器端视觉 E2E。

## 验收标准

- 长翻译只要持续收到 SSE 事件，就不会因从请求开始计算的固定总时长而失败。
- 真正连续空闲达到配置值时，页面显示现有可诊断的翻译超时错误。
- 最终页面仍只展示校验通过的完整翻译，不展示半截 JSON 或不完整块。
- 非翻译用途的请求行为无回归。
- 仓库中不包含真实 API Key 或真实模型输出。
